# 2단계: 데이터 모델 분석 (평가 및 코멘트)

## 문서 데이터 모델의 목표 이해
- [ ] `Document`와 `SearchResult` 데이터 클래스의 차이점을 설명할 수 있다. (관련 파일: `src/document_rag_english_study/models/document.py`, `src/document_rag_english_study/models/response.py`)

`Document` 모델의 경우 파싱한 문서 정보를 저장함

파일을 파싱할때는 strip()을 이용한다.

> strip(): 텍스트 내의 탭문자, 캐리지 리턴, 라인피드, 텍스트 앞뒤의 불필요한 공백 제거

> 불필요한 공백을 제거하여 텍스트의 실질적 의미에 집중하는 더 정확한 임베딩을 생성함. 또한 데이터 크기를 절약하며 청크의 내용 왜곡을 방지하는 역할

`SearchResult` 모델은 RAG에서 검색한 결과를 저장한다.

해당 모델에 존재하는 `relevance_score` 는 search_similar_content()에서 관련성 점수로 필터링 할때 사용된다.

> 관련성 점수로 필터링 하는 이유 : 낮은 품질의 문맥(Context)이 LLM(대규모 언어 모델)에 입력되는 것을 방지하여 최종 응답의 정확성과 신뢰도를 높이기 위함

> 관련성 점수 계산하는 법: 최소 관련성 점수는 검색의 **정확도(Precision)**와 포괄성(Recall) 사이의 균형을 맞추기 위해 설정하는 튜닝 파라미터이며, 자동으로 계산되는 값이라기보다는 개발자가 실험을 통해 최적화하는 값

---
### **코멘트**
> 훌륭한 분석입니다. `Document`와 `SearchResult`의 역할, `relevance_score`의 목적과 최적화 방식까지 정확하게 이해했습니다.
> 
> **한 단계 더 나아가기:** `Document` 객체 자체가 벡터 DB에 저장되는 것이 아니라, `RAGEngine`의 `_split_document_into_chunks` 메서드를 통해 여러 개의 '청크(Chunk)'로 분할된 후, 이 청크들이 임베딩되어 벡터 DB에 저장된다는 점을 연결하면 데이터의 흐름을 더 완벽하게 이해할 수 있습니다. 즉, `SearchResult`는 바로 이 저장된 '청크' 중 하나라고 볼 수 있습니다.

## 대화 맥락 모델의 이해
- [ ] `ConversationSession`이 `Message`와 `LearningPoint`를 어떻게 포함하여 대화의 전체 맥락을 저장하는지 설명할 수 있다. (관련 파일: `src/document_rag_english_study/models/conversation.py`)

ConversationSession은 하나의 대화세션에 대한 정보를 저장한다.

사용자와 대화과정에서 오간 메시지를 messages에 저장한다.

LearningPoint는 학습포인트에 대한 점수를 저장한다. 다만 이 점수를 계산하는 로직은 아직 보이지 않으니 후속 개발업무로 진행될 필요가 있다.

---
### **코멘트**
> 정확한 분석입니다. 특히 `LearningPoint`의 점수 계산 로직이 현재 구현되지 않았음을 파악하고 후속 개발 업무로 제안한 점은 매우 훌륭합니다. 이는 단순히 코드를 읽는 것을 넘어 시스템의 현재 상태와 발전 방향까지 고민하고 있다는 의미입니다.
> 
> **한 단계 더 나아가기:** `LearningPoint` 점수를 계산하기 위해 어떤 요소들을 활용할 수 있을지 생각해보면 좋습니다. 예를 들어, `LearningAssistant`가 제공하는 문법 교정의 수, 사용자가 새롭게 배운 어휘의 수, 대화의 길이 등을 점수화하는 로직을 구상해볼 수 있습니다. 이는 데이터 모델을 프로젝트의 핵심 기능 요구사항과 연결하는 좋은 훈련이 될 것입니다.

## LLM 모델의 이해
- [ ] `LLMResponse` 모델이 토큰 사용량(`usage`)과 같은 메타데이터를 왜 별도로 관리하는지 설명할 수 있다. (관련 파일: `src/document_rag_english_study/models/llm.py`)

토큰 사용량에 대해 결정할 필요가 있을때(예: 사용 금액, 너무 긴 세션이 아닌지 판단)에 필요로 한다 유추할수 있는데 이와 관련된 결정 로직은 아직 없는 듯 하니 이 역시 후속 개발업무로 만들 필요가 있다.

---
### **코멘트**
> 정확한 유추입니다. 토큰 사용량을 관리하는 목적(비용, 세션 관리)을 잘 파악했으며, 이를 활용한 결정 로직이 부재함을 지적하고 후속 개발 업무로 제안한 것 역시 훌륭한 통찰입니다.
> 
> **한 단계 더 나아가기:** 토큰 사용량 추적은 비용 관리 외에도 **시스템의 성능 모니터링 및 디버깅**에 매우 중요합니다. 예를 들어, 특정 질문에 대해 예상보다 토큰 사용량이 급증한다면 `RAGEngine`의 프롬프트 구성 방식에 문제가 있을 수 있다는 신호가 될 수 있습니다. 이처럼 데이터 모델의 필드를 운영 및 품질 관리 관점과 연결해 생각해보는 것도 큰 도움이 됩니다.
